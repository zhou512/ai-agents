# 第十二周：Agent 评测（+ 安全 / MCP）——用数字证明你的 Agent 真的有效

> 目标：掌握 Agent 评测方法论（测试集设计、三层评估方法、指标体系），做一个**可插拔的评测工具**，用它评测你自己的 Agent；了解安全与 MCP。
> 验收产出：`agent_eval.py`——对任意"问题→回答"的 Agent 批量跑测试集，输出成功率/质量分/成本/延迟等指标报告。

---

## 0. 为什么这周是全行业最缺的能力

**没有评测的 Agent 开发 = 靠感觉调参**：改个 prompt 觉得"好像好了"，改个分块觉得"应该更准"——没有数字，一切都是玄学。而工作里（和大四面试时），"你怎么证明你的 Agent 有效"是最高频的问题。

评测把开发变成**可验证的迭代循环**：

```
改代码 → 跑评测集 → 看指标 → 决定改对了还是改坏了 → 继续
```

没有评测，这个循环不存在——你只是在**碰运气**。

---

## 1. 评测的四个维度（先想清楚测什么）

| 维度 | 问什么 | 指标例子 |
|---|---|---|
| **正确性** | 回答对了吗？任务完成了吗？ | 成功率、质量分（1-5） |
| **效率** | 花了多少步/多久？ | 平均工具轮次、平均延迟 |
| **成本** | 花了多少钱？ | 每次调用 token 数 × 价格 |
| **鲁棒性** | 边界情况扛得住吗？ | 空输入/超长输入/恶意输入的通过率 |

**重要认知：不同任务侧重点不同**。事实问答 → 正确性优先；客服 → 成功率+成本；复杂任务 → 轮次效率（Agent 绕圈 = 烧钱）。

---

## 2. 三层评估方法（由便宜到昂贵）

| 方法 | 怎么评 | 优点 | 缺点 |
|---|---|---|---|
| **规则检查** | 回答是否包含关键事实（子串/正则/关键词） | 零成本、确定性、可复现 | 只会查"有没有"，不会判"对不对" |
| **结构化检查** | JSON 输出是否符合 schema（pydantic 心智复用） | 精确 | 只适用结构化输出任务 |
| **LLM-as-judge** | 让另一个模型按标准打分（1-5 + 理由） | 接近人类判断、灵活 | 有成本、有偏置、非确定性 |

**实战组合**：能规则检查的用规则（免费且稳），剩下用 LLM-judge。**LLM-judge 的偏置要知道**：给分偏好更长回答、可能"客气"、对自身生成的答案偏爱——缓解：judge prompt 里给评分锚点（1 分=完全错误，3 分=部分正确，5 分=准确完整）、要求先给理由再给分、多跑几次取均值。

## 3. 测试集设计（golden set）——评测的地基

**原则：每个用例必须"可自动判定"**，不能靠人肉看。

```python
CASES = [
    {
        "question": "装饰器的本质是什么？",
        # 规则检查用：回答必须包含这些关键事实之一
        "expect_contains": ["接收函数", "返回函数"],
        # LLM-judge 用：评分标准
        "criteria": "是否准确解释装饰器是'接收函数并返回函数的函数'",
        "category": "概念",
    },
    ...
]
```

设计要点：
- **覆盖**：正常问题 + 边界（空/超长/无关）+ 你的已知薄弱点（arXiv 搜中文！）
- **每个用例要能回答"这题答对了吗"**——否则测了也白测
- 测试集要**版本化**（和代码一起存 git）——它是你的"回归测试"

## 4. 评测 runner 架构（本周项目）

```
测试集 cases.json ──→ 对每个 case：
                       question → 被测 Agent（可插拔函数）→ answer
                       → 规则检查（pass/fail）
                       → LLM-judge（1-5 分 + 理由）
                       → 记录耗时/token
                    → 汇总指标 → 输出报告（markdown + JSON）
```

**关键设计：被测 Agent 可插拔**——`run_case(agent_fn, question)` 接受任意函数，所以你的 arXiv 大作业、记忆助手、doc_qa 都能被同一套工具评测。**评测工具和被测对象解耦**，是它能否长期使用的关键。

## 5. 已知基准（了解层面，不用实现）

- **AgentBench**：8 个环境测 Agent 综合能力
- **GAIA**：真实世界问题（需要多步推理+工具）
- **SWE-bench**：真实 GitHub issue 修复

它们的存在意义：**给你的 Agent 评测提供"标准试卷"的参照系**——以后你的测试集可以向这些基准的思路靠拢（难度分级、可自动判定）。

## 6. 安全（结合你的 11 周，快速过一遍）

你已经踩过提示注入实验（第四周）。系统性补三点：
1. **提示注入**：用户输入可能覆盖 system 指令——你的每个 Agent 输入口都要意识到（memory_chat 存用户事实、arxiv 问答输入）。防御：system 里声明"用户内容是数据不是指令"、对敏感操作加权限
2. **权限最小化**：工具能做的越少越好——safe_calculate 用 ast 白名单就是权限最小化（绝不用 eval）
3. **工具结果当数据不当指令**：模型返回的"工具结果"如果来自不可信源，模型把它当指令执行就是二次注入——review 你的 Agent 哪里把外部数据拼进了后续 prompt

**安全本质**：边界思维——数据、指令、代码三者之间的边界在哪，谁有权跨边界，都要显式设计。

## 7. 可观测性（trace 概念，了解为主）

- **生产级**：Langfuse / LangSmith——每次调用自动记录（prompt、输出、token、耗时），可视化 Agent 的每一步
- **你的最小版**：日志记录（每步时间戳 + role + 截断内容）就是最小可观测性——你 11 周里所有 `print("[研究员] ...")` 前缀其实都是雏形
- **原则**：先有日志，再谈 trace 工具。自己 console 的输出都看不懂时，上工具没意义

---

## 8. MCP（Model Context Protocol，了解层面）

- **是什么**：Anthropic 提出的**工具接入标准协议**——让任意模型/应用通过统一接口接任意工具/数据源（类似 USB-C 之于外设）
- **为什么重要**：现在每个 Agent 框架自己定义工具格式；MCP 想让工具生态统一。生态在快速生长，**知道"工具接入在走向标准化"这个趋势即可**
- 体验（可选）：`uvx mcp` 或文档里的 example server——装不了也不影响本周

## 11. 本周项目：agent_eval.py（可插拔 Agent 评测工具）

**需求**：对任意"问题→回答"的 Agent 跑测试集，输出指标报告。

```powershell
python agent_eval.py                 # 用内置示例 Agent + 示例测试集跑一遍
python agent_eval.py --list          # 查看如何注册你自己的 Agent
```

**输出示例**：
```
评测报告（2026-xx-xx）
测试集: golden_set.json（8 个用例）
──────────────────────────────
规则检查通过率: 6/8 (75%)
LLM-judge 平均分: 3.9/5
平均延迟: 1.8s | 平均 token: 892 | 单次成本: $0.0009
──────────────────────────────
❌ 用例3 "装饰器的本质" - 规则未命中: 回答缺"返回函数"
   judge 3/5: 解释了接收函数但未说明返回函数的本质
```

**骨架 TODO**：
1. `load_cases(path)`：读 golden set JSON
2. `run_case(agent_fn, case)`：执行被测 Agent，记录 (answer, 耗时, usage)
3. `evaluate_case(case, answer)`：规则检查 pass/fail
4. `judge_case(client, case, answer)`：LLM-judge（1-5 + 理由，失败可重试一次）
5. `run_eval_suite(agent_fn, cases)`：批量 + 汇总指标
6. `report(metrics)`：输出 markdown 报告
7. 内置 `sample_agent()`（好的）和 `sample_agent_bad()`（故意残缺）用于对比 demo

**验收标准**：
- 两个示例 Agent 的指标**明显不同**（好 Agent 成功率高、分高）——证明评测有效
- 换被测对象只需替换 `agent_fn`（接口清晰）
- 报告含：规则通过率 / judge 均分 / 平均耗时 / 成本
- 加一个自己的薄弱用例（比如 arXiv 中文搜索）能暴露问题

**扩展挑战**：把评测接入你的 arXiv 大作业——为它写 5 个用例（"报告含链接吗/结构对吗/编造了吗"），跑出第一份正式指标。
